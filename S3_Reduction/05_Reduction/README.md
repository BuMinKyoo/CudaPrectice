## 왜 리덕션인가

04/05 까지는 **출력이 입력만큼 많았다.** 쓰레드마다 자기 칸이 따로 있어서
옆 쓰레드가 뭘 하는지 알 필요가 없었다. 인덱스 계산만 맞으면 끝이었다.

리덕션은 **출력이 하나다.** 3355만개를 더해서 값 하나를 만든다.
여러 쓰레드가 같은 칸에 기여해야 하니, 여기서 처음으로 **협력**이 필요해진다.

합계·최댓값·내적·노름·소프트맥스가 전부 리덕션이다.

## 배울 것

- **경쟁 상태(race)**: `output[0] += input[i]` 가 왜 틀리는가. 그리고 왜 *가끔은* 맞는가
- **`atomicAdd`**: 읽기-더하기-쓰기를 쪼갤 수 없게 묶는다. 대가는 **줄 서기(경합)**
- **`__syncthreads()`**: 블럭 안 쓰레드 동기화. 왜 `if` 안에 두면 안 되는가
- **convergent 하게 접기**: 일하는 쓰레드를 앞으로 모아 warp divergence 를 없앤다
- **`extern __shared__`**: 런치 때 크기를 정하는 공유 메모리. `<<<블럭, 쓰레드, 공유메모리>>>`
- **segmented**: 블럭마다 구간을 맡고 블럭당 `atomicAdd` 1번 → 블럭 수 제한이 풀린다
- **float 덧셈은 결합법칙이 성립하지 않는다** — 04 의 검증 기준(`mismatch == 0`)이 깨진다

## 네 커널

| | 커널 | 범위 | atomicAdd 호출 | 특징 |
|---|---|---|---:|---|
| 0 | `racySumReductionKernel` | 전체 3355만 | 0 | **틀린 코드.** 비교용 |
| 1 | `atomicSumReductionKernel` | 전체 3355만 | **size** (3355만) | 가장 짧다. 그리고 가장 느리다 |
| 2 | `convergentSumReductionKernel` | 앞쪽 2048개 | 0 | 전역 메모리에서 트리로 접는다 |
| 3 | `sharedMemorySumReductionKernel` | 앞쪽 2048개 | 0 | 공유 메모리에서 접는다 |
| 4 | `segmentedSumReductionKernel` | 전체 3355만 | size/2048 (1.6만) | 2+3 을 합친 실전형 |

**주의 — 2)/3) 은 블럭 하나만 쓴다.** 블럭 하나는 쓰레드 1024개 x 2칸 = 2048칸이
한계라 배열 앞쪽 2048개만 더한다. 그래서

- 2)/3) 의 시간을 1)/4) 와 **직접 비교하면 안 된다** (일의 양이 1만 6천배 차이다)
- 2) 와 3) 끼리만 비교한다 → 전역 메모리 vs 공유 메모리
- 2)/3) 의 합계는 **앞쪽 2048개의 정답**과 비교한다 (코드의 `sumRefOneBlock`)

전체 배열을 제대로 더하는 건 **1) 과 4) 뿐**이고, 이 둘의 차이가 이 예제의 본론이다.

## 접는 방식

```
2) convergent — 반대쪽 절반을 흡수         (input 을 덮어쓴다)
   stride=1024: t0 += t1024, t1 += t1025, ... t1023 += t2047
   stride=512 : t0 += t512,  t1 += t513,  ... t511  += t1023
   stride=256 : ...
   일하는 쓰레드가 항상 threadIdx.x < stride -> 앞쪽에 연속으로 모인다
   -> warp(32개) 단위로 통째로 일하거나 통째로 쉰다 = divergence 없음

   (반대로 "옆칸 흡수" 방식은 짝수 tid 만 일해서 warp 안이 갈라진다)

3) shared — 접는 방식은 2) 와 완전히 동일하다. 장소만 공유 메모리로 옮겼다
4) segmented — 3) 을 블럭마다 하고, 블럭 결과만 atomicAdd 로 합친다
```

## 트리가 경쟁을 없애는 원리 — 이 예제의 핵심

`atomicAdd` 는 경쟁을 **동기화로 막는다.** 3355만 명이 한 칸을 두고 줄을 선다.
트리는 **경쟁 자체가 없는 구조로 바꾼다.**

> **"다 같이 한 칸에 더하기" → "각자 자기 칸에 쓰기"**

작게 보면 (쓰레드 4명, 데이터 8칸):

```
입력:      [ 1   2   3   4   5   6   7   8 ]

stride=4:  t0: in[0] += in[4]  ->  1+5 = 6
           t1: in[1] += in[5]  ->  2+6 = 8
           t2: in[2] += in[6]  ->  3+7 = 10
           t3: in[3] += in[7]  ->  4+8 = 12
           [ 6   8  10  12 ]                   8칸 -> 4칸

stride=2:  [16  20 ]                           4칸 -> 2칸
stride=1:  [36]                                2칸 -> 1칸      (1+2+...+8 = 36)
```

**각 단계에서 쓰레드 `t` 는 `in[t]` 에만 쓴다. `in[t]` 에 쓰는 쓰레드는 `t` 하나뿐이다.**

```
stride=4 에서 쓰는 칸:  t0->in[0], t1->in[1], t2->in[2], t3->in[3]
                        전부 다른 칸. 충돌할 수가 없다
```

그래서 `atomicAdd` 가 필요 없다. 단계 **사이**만 `__syncthreads()` 로 막으면 된다
(다음 단계가 이전 단계의 결과를 읽으므로).

그리고 3355만 번의 순차 덧셈이 `log2(2048) = 11 단계`로 줄어든다.

## 코드 읽기 — 헷갈리는 곳

### `i` 와 `t`, 좌표계가 두 개다

```c
unsigned int segment = 2 * blockDim.x * blockIdx.x;
unsigned int i = segment + threadIdx.x;    // 전역용
unsigned int t = threadIdx.x;              // 공유용
```

| | 쓰는 곳 | 범위 | 성질 |
|---|---|---|---|
| `i` | `input[i]` (전역) | 0 ~ 3355만 | **전체에서 유일** |
| `t` | `inputShared[t]` (공유) | 0 ~ 1023 | **블럭 안에서만 유일** (블럭마다 반복) |

**메모리가 다르면 좌표계도 다르다.** 전역은 모두가 공유하니 전역 번호가 필요하고,
공유 메모리는 블럭마다 따로 할당되니 블럭 안 번호면 충분하다.
`blockIdx.x` 가 `segment` 계산에만 나오고 `inputShared` 쪽엔 안 나오는 이유.

```
블록 0              블록 1              블록 16383
┌──────────────┐  ┌──────────────┐    ┌──────────────┐
│ inputShared  │  │ inputShared  │ .. │ inputShared  │
│  [0 .. 1023] │  │  [0 .. 1023] │    │  [0 .. 1023] │
└──────────────┘  └──────────────┘    └──────────────┘
  완전히 별개의 메모리. threadIdx.x 가 반복돼도 겹치지 않는다
```

### `input[i] + input[i + blockDim.x]` — 왜 `blockDim.x` 를 더하나

블럭 하나가 **2048칸**을 맡는데 쓰레드는 **1024명**뿐이다. 한 명이 두 칸을 맡아야 한다.
그 두 칸을 **구간을 반으로 갈라서** 짝짓는다.

```
     앞쪽 절반 (1024칸)          뒤쪽 절반 (1024칸)
   ┌──────────────────┐       ┌──────────────────┐
   │ segment+0 ... +1023│  +  │ segment+1024 ... +2047│
   └──────────────────┘       └──────────────────┘
      t0 t1 ... t1023             t0 t1 ... t1023
```

`blockDim.x` 가 곧 "앞쪽 절반의 길이"라, 그만큼 더하면 뒤쪽의 같은 자리가 나온다.

**왜 붙어 있는 두 칸(`input[2i]`, `input[2i+1]`)이 아닌가 — coalescing 때문이다.**

```
붙은 두 칸:  t0->0, t1->2, t2->4 ...   stride 2 -> warp 가 256바이트를 덮는데
                                        쓰는 건 128바이트.  효율 50%   BAD

절반 갈라:   t0->0, t1->1, t2->2 ...   연속 32칸 = 128바이트.  효율 100%  OK
             (두 번째 읽기도 마찬가지)
```

그리고 읽는 김에 더하므로 **트리 한 단계를 공짜로 번다** (2048 -> 1024).
그래서 루프가 `blockDim.x / 2 = 512` 부터 시작한다.

### `if (t < stride)` — "아직 유효한 범위 안의 쓰레드만"

| stride | 통과하는 쓰레드 | 일하는 수 | 남는 데이터 |
|---|---|---:|---|
| 512 | t = 0 ~ 511 | 512 | 1024 -> 512 |
| 256 | t = 0 ~ 255 | 256 | 512 -> 256 |
| 128 | t = 0 ~ 127 | 128 | 256 -> 128 |
| ... | | | |
| 2 | t = 0 ~ 1 | 2 | 4 -> 2 |
| 1 | t = 0 | **1** | 2 -> **1** |

데이터가 반씩 줄어드니 일꾼도 반씩 줄어든다. **이게 트리 그 자체다.**
`if` 가 없으면 `inputShared[t + stride]` 가 배열 밖을 읽고, 이미 쓴 영역을 또 건드린다.

다만 뒷단계는 비효율적이다 — `stride=1` 일 때 1024명 중 1명만 일하고
나머지 1023명은 `__syncthreads()` 에서 기다린다. (개선은 warp shuffle 로)

### `stride` 가 0 이 되면서 끝난다

```c
for (unsigned int stride = blockDim.x / 2; stride >= 1; stride /= 2)
```

정수 나눗셈이라 `1 / 2 = 0` 이다. 소수점이 없다.

```
512 -> 256 -> 128 -> 64 -> 32 -> 16 -> 8 -> 4 -> 2 -> 1 -> 0 에서 종료
```

**`unsigned` 함정:** 조건을 `stride >= 0` 으로 쓰면 무한 루프다.
unsigned 는 음수가 될 수 없어 항상 참이고, `0/2 = 0` 이라 영원히 0이다.
커널 안 무한 루프는 TDR(2초)에 걸려 드라이버가 리셋된다.

## atomicAdd

```c
float old = atomicAdd(주소, 값);    // 반환값은 "더하기 전" 값
```

읽기-더하기-쓰기를 **쪼갤 수 없는 한 덩어리**로 처리한다.

반환값은 순번표로 자주 쓴다:
```c
int myIndex = atomicAdd(&counter, 1);    // 각 쓰레드가 유일한 번호를 받는다
```

**범위**

```c
atomicAdd(전역_포인터, v);    // GPU 전체 (모든 블럭, 모든 SM) 에 걸쳐 원자적
atomicAdd(공유_포인터, v);    // 그 블럭 안에서만 원자적 (더 빠름)
```

블럭 사이에는 `__syncthreads()` 가 안 통하므로, **전역 atomic 이 블럭 간 통신의
거의 유일한 수단**이다 (나머지 하나는 커널을 나누는 것).

| 범위 | 동기화 수단 |
|---|---|
| warp 안 | 자동 (같은 명령) |
| **블럭 안** | `__syncthreads()` |
| **블럭 사이** | **전역 atomic** 또는 **커널 분리** |

**타입:** int / unsigned / float 는 오래전부터, **double 은 sm_60(Pascal) 이상.**
P2000 은 sm_61 이라 double 도 된다. atomicMax/Min/Exch/CAS 등도 있다.

**정확하지만 결정론적이지 않다.** 더해지는 순서가 실행마다 달라서, float 덧셈의
결합법칙 불성립과 겹쳐 결과가 마지막 비트 수준에서 흔들린다.
racy 처럼 크게 틀리는 것과는 다른 종류의 문제다.

## 부동소수점 — 04 의 규칙이 깨지는 곳

04 는 값을 **옮기기만** 했으므로 CPU 와 GPU 결과가 비트 단위로 같아야 했고,
`mismatch == 0` 이 정답이었다. 리덕션은 **더한다.** 그리고 float 덧셈은

```
(a + b) + c  !=  a + (b + c)
```

더하는 순서가 바뀌면 답이 바뀐다. 그래서 **상대오차**로 검증한다.

이 예제가 `sumCpu`(float 순차합) 말고 `sumRef`(double 누적)를 따로 두는 이유가 이것이다.
float 로 3355만번 누적하면 **`sumCpu` 자체가 정답이 아니다.** 누적값이 1600만쯤
됐을 때 거기에 0.5 를 더하면 float 유효자리 24비트(약 1670만)가 모자라서 작은 값이
통째로 버려진다. 표를 보면 `sumCpu` 의 오차가 4) 보다 훨씬 크다 —
**GPU 트리합이 CPU 순차합보다 정확하다.**

- 직접 적어보기 — 트리로 접으면 한 값이 최종 결과에 도달하기까지 덧셈을 몇 번 거치는가.
  순차합은 몇 번인가:
- 여러 번 실행하면 1) 과 4) 의 합계 끝자리가 흔들린다 (2)/3) 은 안 흔들린다).
  `atomicAdd` 의 무엇 때문인가. 재현성이 필요한 계산에서 이게 왜 문제인가:
