# 06_Reduction — 협력과 리덕션 (S3-1)

## 왜 리덕션인가

04/05 까지는 **출력이 입력만큼 많았다.** 스레드마다 자기 칸이 따로 있어서
옆 스레드가 뭘 하는지 알 필요가 없었다. 인덱스 계산만 맞으면 끝이었다.

리덕션은 **출력이 하나다.** 1678만개를 더해서 값 하나를 만든다.
여러 스레드가 같은 결과에 기여해야 하니, 여기서 처음으로 **협력**이 필요해진다.

- 누가 누구 값을 더할지 — 공유 메모리 + `__syncthreads()`
- warp 안에서 조건이 갈리면 어떻게 되는지 — **divergence**
- 블록끼리는 어떻게 합칠지 — 다중 패스 vs `atomicAdd`

그리고 합계·최댓값·내적·노름·히스토그램·소프트맥스 전부 리덕션이다.
전치와 달리 **응용에서 계속 다시 나온다.**

## 배울 것

- **warp divergence**: warp 32개 스레드는 명령을 함께 실행한다. 조건이 갈리면 양쪽을 순차 실행한다
- **`__syncthreads()` 를 `if` 안에 두면 안 되는 이유**: 모든 스레드가 도달해야 통과하는 장벽이다
- 리덕션에서의 **bank conflict** — 04 에서 본 그 bank 가 접는 방향 때문에 다시 등장한다
- **접는 방향을 뒤집으면** divergence 와 conflict 가 동시에 사라진다 (관용적 형태)
- **스레드당 일을 늘리기**: 블록 수를 묶고 grid-stride 로 먼저 접어 트리 높이를 낮춘다
- **`__shfl_down_sync`**: 같은 warp 라면 공유 메모리 없이 레지스터를 직접 주고받는다
- **`atomicAdd`**: 다중 패스를 1패스로. 대가는 재현성
- **float 덧셈은 결합법칙이 성립하지 않는다** — 04 의 검증 기준(`mismatch == 0`)이 여기서 깨진다

## 여섯 커널

구하는 값은 **전부 똑같은 합계다.** 접는 방법만 다르다.

| | 커널 | divergence | bank conflict | 스레드당 칸 | 패스 |
|---|---|---|---|---|---|
| A | `ReduceDivergent` | **있음** (`tid % (2*s)`) | 없음 | 1 | 3 |
| B | `ReduceNoDivergent` | 없음 | **있음** (최대 32-way) | 1 | 3 |
| C | `ReduceSequential` | 없음 | 없음 | 1 | 3 |
| D | `ReduceGridStride` | 없음 | 없음 | 여러 개 | 2 |
| E | `ReduceShuffle` | 없음 | 없음 (마지막 warp 는 shuffle) | 여러 개 | 2 |
| F | `ReduceShuffleAtomic` | 없음 | 없음 | 여러 개 | **1** |

A → B → C 는 **같은 알고리즘의 인덱스만 바꾼 것**이다. 여기서 나오는 차이가
divergence 와 bank conflict 의 값이다.

C → D 는 알고리즘이 바뀐다. 트리를 낮추는 쪽으로.

## 접는 방향 (A/B vs C)

```
A)  옆칸을 흡수          B)  일할 스레드를 앞으로      C)  반대쪽 절반을 흡수
    s=1                     s=1                          s=128
    t0 += t1                t0 += t1                     t0   += t128
    t2 += t3                t1 += t3  (index=2*s*tid)    t1   += t129
    t4 += t5                t2 += t5                     ...
    (짝수 tid 만)            (앞쪽 tid 만)                 t127 += t255
    -> warp 내부가 갈린다    -> 공유 메모리가 2,4,8칸씩     -> tid, tid+s 로 연속
                               뛴다 (conflict)               (충돌 0, 갈림 없음)
```

## 해석 (직접 적기)

- A → B 의 차이. 더하는 횟수는 똑같은데 왜 빨라졌나:
- B → C 의 차이. B 에서 `index = 2*s*tid` 가 s=16 일 때 어떤 bank 들을 치는가:
- C → D 의 차이가 A → C 보다 큰 이유. D 에서 실제로 줄어든 것은 무엇인가
  (덧셈 횟수? 커널 런치 횟수? 놀고 있는 스레드 비율?):
- D → E 의 차이. `__syncthreads()` 5번과 공유 메모리 왕복 5번을 없앤 값은 얼마였나:
- E → F 의 차이. 패스가 2번에서 1번으로 줄었는데 시간은 기대만큼 줄었나. 아니라면 왜:
- 이 GPU 의 이론 대역폭 대비 E 의 실효 대역폭은 몇 % 인가.
  리덕션은 읽기만 하는데 `04` 의 Copy 기준선과 비교하면?

## 부동소수점 — 04 의 규칙이 깨지는 곳

04 는 값을 **옮기기만** 했으므로 CPU 와 GPU 결과가 비트 단위로 같아야 했고,
`mismatch == 0` 이 정답이었다. 리덕션은 **더한다.** 그리고 float 덧셈은

```
(a + b) + c  !=  a + (b + c)
```

더하는 순서가 바뀌면 답이 바뀐다. 그래서 리덕션에서는 비트 일치가 아니라
**상대오차**로 검증해야 한다.

그런데 표를 보면 이상한 일이 벌어진다. **GPU 트리합이 CPU 순차합보다 정확하다.**

- 직접 적어보기 — CPU 순차합은 누적값이 800만쯤 됐을 때 거기에 0.5 를 더한다.
  float 유효자리는 24비트(약 1670만)뿐이다. 이때 무슨 일이 일어나나:
- 트리합에서 한 값이 최종 결과에 도달하기까지 거치는 덧셈 횟수는 몇 번인가
  (1678만개, 순차합과 비교):
- Kahan 합은 float 만 쓰는데도 왜 정확한가. 대신 무엇을 지불했나 (표의 시간):
- F) 를 여러 번 실행하면 합계 끝자리가 흔들린다. `atomicAdd` 의 무엇 때문인가.
  재현성이 필요한 계산에서 이게 왜 문제인가:

## 생각해볼 것

- **`__syncthreads()` 를 `if (tid < s)` 안으로 옮기면?** — 실행해보기 전에 예측부터.
  (멈춘다면 Ctrl+C. 이게 왜 위험한 버그인지는 결과가 아니라 *이유*가 중요하다)
- C 커널에서 `__syncthreads()` 를 아예 지우면? **항상** 틀리나, 가끔 틀리나?
  s 가 32 이하일 때만 지우면 어떻게 되나 (→ S4 에서 `compute-sanitizer` 로 확인)
- E 의 `WarpReduceSum` 에서 mask 를 `0xffffffff` 대신 `__activemask()` 로 바꾸면?
  둘 중 어느 게 옳은지, 왜 여기서는 둘 다 동작하는지
- `ELEMS_PER_THREAD` 를 1, 4, 16, 64 로 바꿔가며 D/E 를 측정 — 최적점이 있나?
- `GRID_STRIDE_CAP` 을 SM 수 x 블록/SM (`00_DeviceQuery` 출력) 로 맞추면?
- **합계가 아니라 최댓값**으로 바꿔보기. 초기값 `0.0f` 를 무엇으로 바꿔야 하나?
  `atomicAdd` 대신 무엇을 쓰나?
- 입력을 전부 `1.0f` 로 채우면 상대오차 표가 어떻게 되나. 왜 그렇게 되나?
