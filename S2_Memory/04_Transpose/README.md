# 04_Transpose — coalescing 과 공유 메모리 (S2-1)

## 왜 전치인가

전치는 **계산이 하나도 없다.** 값을 다른 자리로 옮기기만 한다.
그래서 성능 차이가 전부 **메모리 접근 패턴**에서 나온다 — S2 주제를 보기에 가장 깨끗한 소재다.

02 에서 "블록 모양이 성능을 바꾼다"까지 봤다면, 여기서는 그 이유를 정면으로 다룬다.

## 배울 것

- **coalescing**: warp 32개 스레드가 연속된 주소를 건드려야 트랜잭션이 1번으로 합쳐진다
- 읽기와 쓰기 중 **한쪽만 흩어져도** 그만큼 느려진다 (B 커널)
- **공유 메모리(`__shared__`)**: SM 안에 있는 빠른 메모리. 전역 메모리에서 흩어지는 대신 여기서 뒤집는다
- **`__syncthreads()`**: 블록 안 스레드들이 서로를 기다리는 지점. 왜 꼭 필요한가
- **bank conflict**: 공유 메모리도 공짜가 아니다. 32개 bank 를 동시에 쳐야 한다
- 패딩 한 칸(`[32][33]`)으로 bank conflict 를 없애는 표준 기법

## 네 커널

| | 커널 | 전역 읽기 | 전역 쓰기 | 공유 메모리 |
|---|---|---|---|---|
| A | `Copy` | 연속 | 연속 | 안 씀 |
| B | `TransposeNaive` | 연속 | **흩어짐** | 안 씀 |
| C | `TransposeShared` | 연속 | 연속 | **bank conflict** |
| D | `TransposeSharedPadded` | 연속 | 연속 | 충돌 없음 |

**A 는 전치가 아니다.** 그냥 복사다. 이 GPU 가 낼 수 있는 속도의 **상한선**으로 쓴다.
B~D 가 A 에 얼마나 근접하는지가 이 예제의 관전 포인트다.

## 실행

```
Release | x64 로 빌드 후 실행
04_Transpose.exe          기본 4096 x 4096 (행렬 하나 64 MB)
04_Transpose.exe 2048     크기 변경
```

## 생각해볼 것

- `TILE_DIM` 을 16 이나 64 로 바꾸면? (`BLOCK_ROWS` 도 같이 조정해야 한다)
- `__syncthreads()` 를 지우면 결과가 어떻게 되나. **항상** 틀리나, 가끔 틀리나?
  (가끔 틀린다면 그게 더 무서운 종류의 버그다 → S4 에서 다시 본다)
- B 커널에서 읽기와 쓰기를 뒤집으면 (`out[(y+j)*n+x] = in[x*n+(y+j)]`) 시간이 달라지나?
  읽기 비연속과 쓰기 비연속 중 어느 쪽이 더 비싼가?
- N 을 4096 대신 4097 로 주면? (타일 경계가 안 맞을 때 가드가 어떻게 동작하는지)

## 확인해볼 도구 (S4 예고)

추측으로 끝내지 말고 측정할 수 있다. Nsight Compute 가 깔려 있다면:

```
ncu --metrics l1tex__t_sectors_pipe_lsu_mem_global_op_st.sum,smsp__sass_l1tex_data_bank_conflicts_pipe_lsu_mem_shared.sum 04_Transpose.exe 1024
```

- 앞 지표: 전역 쓰기 트랜잭션 수 → B 가 C/D 보다 훨씬 클 것
- 뒤 지표: 공유 메모리 bank conflict 수 → C 에만 크게 잡히고 D 는 0 에 가까울 것
